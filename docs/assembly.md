# assembly.py

`assembly.py` is sequence-level bookkeeping: did I actually build the thing I think I built. It checks that a motif sits exactly where it should, that a graft doesn't overlap something protected, that a graft fits inside its window, and that an assembled sequence matches its blueprint piece by piece. It knows nothing about free energy, K_open, K_CK, or fold-change (that's `thermo.py`), and it does no structure prediction at all, just string and position arithmetic on a sequence you already have. The main entry point, `verify_full_assembly`, runs every individual check (`check_protected_region`, `check_graft_overlap`, `check_latch_fit`) plus per-segment content checks and returns a full checklist rather than one collapsed boolean, so a UI can render it as a real pass/fail list. None of the dataclasses here (`ProtectedRegion`, `LatchWindow`, `GraftSpec`) assume a specific motif or binder; ECLIPSE's actual SmBiT position, latch window, and binder sequence live only in the test files, supplied as arguments.

The one real trap in this module is `filter_safe_variants`, the bridge function that takes `liability.py`'s suggested mutations and checks them against a protected region. It does zero coordinate translation: `liability.py`'s mutation positions are always local to the binder string it was given, not the binder's position inside a larger assembly. Feed it raw output without first applying `offset = binder_start_in_assembly - 1` to every mutation, and you get a meaningless result, a false pass or false reject with no real relationship to whether the mutation actually lands in the protected region. This isn't a bug, `filter_safe_variants` has no way to know where the binder sits unless told, but it makes the offset entirely the caller's responsibility, every time. The import dependency also runs one way: `assembly.py` imports `VariantSuggestion` from `models.py` to make this bridge possible, but `liability.py` has no idea `assembly.py` or the concept of a "protected region" exists at all.
