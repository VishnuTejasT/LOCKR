# models.py

`models.py` is the shared vocabulary: every dataclass the other modules pass around, with no real logic beyond `SensorParams.luckey_ratio`, a named convenience for `lucKey/K_CK` so every module computes that ratio the same way. `SensorParams` (frozen, so it can't be mutated out from under shared callers) holds the four numbers pinning down a sensor's operating point, `K_open`, `K_CK`, `lucKey`, `RT`; `DEFAULT_PARAMS` is the shared instance using ECLIPSE's own base-scaffold values (`K_open=1e-3`, `K_CK=1e-8`, `lucKey=500nM`, `RT=0.592`). The rest of the file is result shapes for the other modules: `BinderSequence` (a normalized, 1-indexed sequence wrapper), `FoldChangeResult`/`ScanResult`/`RegimeResult` from `thermo.py`, `ChargeResult`/`Liability`/`LiabilityReport`/`VariantSuggestion` from `charge.py`/`liability.py`, and the assembly-side `ProtectedRegion`/`LatchWindow`/`GraftSpec`, all fields caller-supplied, nothing ECLIPSE-specific baked in.

Two things in this file are worth flagging. K_CK's exact definition, lucKey↔cage Kd or lucKey↔SmBiT Kd, was genuinely ambiguous across the source docs at one point; it's since been standardized as lucKey↔SmBiT epitope on the open cage, and this file's own TODO comment predates that resolution. And `luckey_ratio` is a diagnostic dominance ratio, not an achievable fold-change ceiling, an earlier version of this codebase conflated the two. A ratio of 50 doesn't mean 50x fold-change is reachable; the real ceiling for a given finite `pull` comes from `thermo.max_fold_change` and can land well below the ratio itself.
